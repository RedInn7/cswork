# 令牌桶限流服务

做一个独立的限流服务：其他服务在处理请求前先来问一句「这个 key 现在还能放行吗」。每个 key 一个令牌桶，桶满时可以突发，空了以后按固定速率恢复。语言和框架不限。

## 接口

所有请求和响应都是 JSON。key 只含字母、数字和 `_ . : -`，长度 1–64。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `PUT` | `/limits/{key}` | 请求体 `{"capacity": 整数 ≥ 1, "refill_per_sec": 数字 > 0}`。新建或替换配置，桶重新装满。返回 200 和配置。 |
| `GET` | `/limits/{key}` | 返回配置和当前令牌数 `tokens`（向下取整）。 |
| `POST` | `/limits/{key}/take` | 请求体可选 `{"tokens": n}`，默认 1。够就扣掉，返回 200 `{"allowed": true, "remaining": 剩余（向下取整）}`；不够返回 429 `{"allowed": false, "remaining": …, "retry_after_ms": 还要等多少毫秒}`，并带 `Retry-After` 头（秒，向上取整，至少 1）。 |
| `DELETE` | `/limits/{key}` | 删除，返回 204。 |

错误：没配置过的 key 返回 404；配置不合法、请求体不是 JSON、`tokens` 不是 1 到 capacity 之间的整数，返回 400。

## 约束

- 令牌按时间连续恢复（不是每秒整点补一次），最多补到 capacity。
- 并发请求不能多放行：60 个请求同时打到 25 个令牌的桶上，正好 25 个成功。
- 不能依赖外部存储，内存里实现即可；时间用单调时钟，不要用墙上时间。

## 加分项

- 加一种滑动窗口日志算法，用请求体里的 `algorithm` 选择，写一段说明比较两者的内存和精度。
- 清理长期不用的 key，内存不随 key 数无限增长。
- 多实例部署时怎么共享状态：用 Redis 的 Lua 脚本实现同样的语义，并说明时钟从哪里来。
- 压测：给出单机 QPS 和 p99 延迟，以及锁的粒度对它的影响。
