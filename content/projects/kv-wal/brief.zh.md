# 带 WAL 和压缩的 KV 存储

从零写一个单机的持久化键值存储：每次写入先追加到预写日志（WAL）并刷盘再确认，进程被杀、断电后重启都能恢复；日志越来越长时用压缩（compaction）把它缩回去。不能用 SQLite、LevelDB、RocksDB 这类现成的存储引擎。语言不限。

## 用法

```
你的程序 --dir 数据目录
```

从标准输入一行读一条命令，每条命令往标准输出写一行回复，写完立即 flush。标准输入结束时正常退出，退出码 0。

| 命令 | 回复 |
| --- | --- |
| `SET key value` | `OK`。key 是第一个空格前的部分（不含空格）；value 是其后的整行，可以有空格和 UTF-8 字符，不能为空。 |
| `GET key` | 值本身；不存在回复 `(nil)`。 |
| `DEL key` | 存在回复 `1`，不存在回复 `0`。 |
| `COMPACT` | 压缩完回复 `OK`。 |
| 其他、缺参数 | 以 `ERR` 开头的一行。 |

## 规则

- **先持久化再确认**：`SET` 和 `DEL` 在回复之前必须已经写进日志并 fsync。回复了 `OK` 的写入，进程被 `kill -9` 后重启必须还在。
- **崩溃恢复**：重启时重放日志。最后一条记录可能只写了一半（断电），必须能识别并忽略它（比如每条记录带长度和校验和），并且之后的新写入不能接在半条记录后面丢掉。验收脚本会在你最后写的那个文件末尾追加几个垃圾字节来模拟这种情况，所以请让日志是最后被写的文件。
- **压缩**：`COMPACT` 把被覆盖和被删除的旧记录清掉。300 次覆盖同一个 2 KB 的值之后，压缩应该让目录从 600 KB 以上降到 100 KB 以下。压缩过程中任何时刻被杀，重启后数据都不能丢（比如写临时文件、fsync、再原子 rename）。
- 被删除的 key 在压缩和重启之后也必须还是删除状态。

## 约束

- 所有数据可以放在内存里做索引，只要求日志和压缩正确。
- 写下你的日志记录格式，以及每一步 fsync 是为了防什么。

## 加分项

- 组提交（group commit）：多个写入攒一次 fsync，测一下吞吐提升多少。
- 数据量大于内存：把压缩结果写成有序文件（SSTable），内存里只放稀疏索引。
- 后台自动压缩，压缩时不阻塞读写。
- 加一层 TCP 或 HTTP 接口，测并发写的吞吐。
