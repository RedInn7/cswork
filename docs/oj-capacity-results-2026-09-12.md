# OJ 四核机器容量对照

结论：增加实际评测容量有效。10 份同时提交时，尾部等待降低约 32%–44%；CPU 实测从约 2 核提高到约 3 核。**这是隔离对照结果，不代表已经上线，也还没达到高并发下全部秒回。**

## 配置

同一台线上 4 核、24GB 机器，串行运行两套隔离测试，不改正式评测队列或数据库。

| 配置 | 同时评测提交 | Runner 执行槽 | Runner CPU 上限 | GOMAXPROCS |
| --- | ---: | ---: | ---: | ---: |
| 原配置 | 1 | 2 | 2 核 | 2 |
| 候选配置 | 2 | 4 | 3 核 | 3 |

Runner 内存上限均为 4GB。Runner 最多使用 3 核，剩余算力由网页、worker 调度等服务共享；这不是独占保留或 CPU 绑核。

## 提交到结果

单位：秒。冷 = 未命中编译缓存；热 = 已预热、实测命中。每种组合一轮；单提交组只有一个样本，10 并发组的 p95 等于本轮最慢值。

| 语言 | 并发 | 缓存 | 总时延 p95：原 → 新 | 排队 p95：原 → 新 |
| --- | ---: | --- | --- | --- |
| C++ | 1 | 冷 | 2.474 → 2.478 | 0.045 → 0.034 |
| C++ | 1 | 热 | 1.056 → 1.052 | 0.041 → 0.031 |
| C++ | 10 | 冷 | 24.808 → 13.794 | 22.306 → 11.031 |
| C++ | 10 | 热 | 10.244 → 6.120 | 9.228 → 4.926 |
| Java | 1 | 冷 | 3.844 → 3.360 | 0.032 → 0.019 |
| Java | 1 | 热 | 2.522 → 2.329 | 0.024 → 0.012 |
| Java | 10 | 冷 | 38.708 → 25.843 | 34.797 → 20.704 |
| Java | 10 | 热 | 25.546 → 17.333 | 22.957 → 13.955 |

共 88 份正式测量、44 份预热，全部 28/28 AC，无错误、无重试。测试为同一账号的正确 Two Sum 程序，不是 10 个真实用户。

## 有没有真正用到更多 CPU

读取整个 Docker cgroup 的 `usage_usec` 增量除以墙钟时间，包含编译和评测子进程，不使用网页上“单测试点耗时”推算 CPU。

| 10 并发组 | 平均使用核数：原 → 新 | 同期首页 p95：原 → 新 |
| --- | --- | --- |
| C++ 冷 | 1.296 → 2.426 | 18.7 → 44.9 ms |
| C++ 热 | 1.405 → 1.594 | 16.7 → 26.0 ms |
| Java 冷 | 1.919 → 2.973 | 22.2 → 29.9 ms |
| Java 热 | 1.920 → 2.468 | 21.5 → 26.4 ms |

CPU 和网页窗口包含热身；提交时延不包含热身。首组窗口还包含数据库备份和 worker 启动，因此不拿首组平均 CPU 作容量结论。

另做四个并发纯 CPU 任务，每个实际消耗约 2 CPU 秒：

| 指标 | 原配置 | 候选配置 |
| --- | ---: | ---: |
| 四任务总墙钟 | 4.128 秒 | 2.690 秒 |
| Runner 累计 CPU | 8.086 秒 | 8.084 秒 |
| 平均核数 | 1.959 | 3.005 |
| 同期首页 p95 | 26.0 ms | 24.2 ms |

八个 CPU 探针任务均通过。3.005 是短窗口采样结果，不能解释为突破 3 核配置上限。网页每秒请求一次本机 `127.0.0.1:4317/`；全部返回 200，无超时。提交测试各组网页 p95 的最大值为原配置 123.1ms、候选 97.5ms，均发生在包含启动的首组；这不是合并所有请求计算的全局 p95。

补充真实 worker 准入回归：普通任务实际重叠 1.253 秒；9MiB 数据快照、16MiB 输出上限任务均与普通任务保持不重叠；等待独占的任务取消后未进入评测，后继普通任务可以继续并行。独立复跑 CPU 探针为 3.004 核，首页 p95 16.7ms。这验证了本次并行与大任务串行规则，不等于穷尽所有内存风险。

## 边界

- 经过真实 worker、编译器、隔离 Runner；使用在线备份出的私有数据库和独立 Redis 队列。未经过提交 API、用户限流、外网或浏览器轮询，不可当作端到端 SLA 或 LeetCode 对比结论。
- 这是小样本容量验证，不是持续高负载、混合难题或最大输入/输出内存测试。Worker 峰值 RSS 约 163 → 165 MiB，只对应这批题目，不能证明所有负载的内存上限。
- 共享机器有其他服务。首页探针仅用于观察明显干扰，不能代替全站回归或其他应用监控。
- 测试容器、复制数据库、独立队列已清理；没有改动正式用户数据。

复用脚本：`tests/oj-capacity-benchmark.sh`、`tests/oj-capacity-benchmark.mjs`，基于 `tests/oj-latency-load.mjs`。原始 JSON 保存在本次任务的 `output/oj-capacity-2026-09-12/`，不随仓库提交。
