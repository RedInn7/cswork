# 50 人同时提交评测：服务器实测

结论：现有线上版本能接收 50 个不同用户同时提交并正确返回结果，不需要把执行并发改成 50。**能接收不等于都能秒回**：这次全 Java 的尾部等待超过一分钟。

测试日期：2026-10-08 UTC。线上基线：`d37570e153496fc3b00227e590a0e2b4ba0b29a2`。

## 结果

每轮 50 个独立账号，在约 15–20 毫秒内发起提交；每份正确答案评测 28 个用例。共 4 轮、200 份正式测量，各轮均成功接收 50 份，结果正确，无意外 429/5xx、丢单、重试或卡死。

| 场景                                                  | 接收请求 P95 | 收到结果 P95 | 最慢结果 |
| ----------------------------------------------------- | -----------: | -----------: | -------: |
| C++ / Java / Python，全部正确                         |      0.67 秒 |     28.88 秒 | 31.04 秒 |
| 混合语言，45 份正确、5 份 Python 错误                 |      0.67 秒 |     26.48 秒 | 27.65 秒 |
| 全部 Java，全部正确                                   |      0.58 秒 |     73.07 秒 | 75.78 秒 |
| 混合语言，45 份正确、5 份不同语言错误（最终脚本复跑） |      0.65 秒 |     27.50 秒 | 28.30 秒 |

错误答案在首个失败用例停止，测试检查了终态和仅 ordinal=0 一条结果；这份压力脚本未直接断言 HTTP 的 firstFailure 字段。额外通过 HTTP 验证了未登录拒绝、跨账号读取拒绝、同账号两份活动提交的限制；重复请求不重复入队由独立单元回归验证，不混称为压测覆盖。报告里的一个 429 是主动测试同账号限制的预期结果，不是 50 人突发被拒。

## 测试环境和边界

- 用户自己的 4 核、24GB 服务器；独立 runner 复用线上镜像，4 执行槽、3 核 CPU 上限、4GB 内存，worker 同时处理 2 份普通提交。
- 使用线上原有 web/worker 构建文件，真实 HTTP 提交、持久化 outbox、队列、编译器、沙箱和长轮询。用户会话由测试预置，不包含登录握手耗时。
- 新建小型临时数据库和 50 个合成账号，不读取、复制或修改生产数据库。独立 Redis 队列，临时数据放内存文件系统，避免服务器剩余约 610MB 磁盘被写满。
- web/worker 是隔离子进程，不在正式 systemd 的 CPU/内存控制组内；HTTP 从服务器本机发起，不包含用户网络、浏览器渲染、Nginx/TLS。不能据此承诺完整生产 SLA。
- 题目是 28 个小型整数求和用例，覆盖三个语言运行时和队列突发，不代表所有复杂题、大输入、高内存、超时程序的表现。各轮源代码不同、未主动预热，但没有采集编译缓存命中事件，不能宣称经证实全部冷缓存。
- CPU 两个瞬时观察约为 2.98 / 3.03 核（采样误差），网页探针两次返回 200，分别约 267ms / 39ms；不是完整窗口 CPU 平均值或网页 P95。
- 接收 P95≤2 秒、全部结果≤180 秒是测试的明确通过条件，不等于产品性能承诺。报告另列 30 秒与 60 秒结果 P95；全 Java 两项均不满足，没有放宽阈值隐藏慢结果。

## 保持现有保护

全局最多 128 份活动提交、每用户最多 2 份、每分钟正式提交 6 次。大快照和高内存题仍独占执行，未为追求并发数量取消这些保护。50 份提交是排队执行，不是 50 个程序同时占用 CPU。

如果产品目标是“50 人同时提交、几秒内全部完成”，当前证据不支持；需要单独优化运行开销或增加评测计算资源，再以相同负载对照验证。
