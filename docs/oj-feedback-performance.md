# OJ 提交反馈优化与隔离压测

## 本轮改动

- outbox 派发周期 200ms → 50ms。保留单次 drain 合并、128 条批次上限与持久化重试。
- POST 返回原有权限过滤后的完整提交详情和 watchToken，客户端省去一次额外 GET。旧版精简回执仍兼容。
- 取消会中止旧提交详情请求，防止晚到的 running 覆盖 cancelled。
- 修复 Go 只读 GOCACHE 的定期 trim 写入错误：私有 `/tmp/go-cache` 使用目录和只读种子文件链接，trim/README 元数据使用私有常规文件。共享 `/usr` 仍只读，不复制约 164MiB 种子，也不放宽沙箱权限。
- 前台编译缓存 8 → 16 项，后台仍最多 2 项，TTL 仍为 5 分钟。每份产物已有 16MiB 上限，保留产物预算最多 288MiB（不含在途编译和运行内存）。按用户、语言、完整源码隔离，不缓存判题结果。
- 浏览器本地 Performance measure `cswork:oj:click-to-feedback`：从提交处理开始，到终态 React commit 后的绘制机会。它不是纯程序 runtime，也不是精确的显示器呈现时间。取消和后台终态不计入；不上传身份、题目或代码。

## 测量边界

`tests/oj-latency-load.mjs` 只在显式指定的本机 5053 隔离沙箱运行。它对源 SQLite 做只读在线备份，在私有临时副本及唯一测试队列内提交，最终清理自己的数据与任务。每份正确解必须通过同一个 Two Sum 完整 28 测试。

此脚本直接入队，绕过 API 的每用户配额和浏览器，因此衡量的是 **提交入库到最终结果落库**，不是用户点击到看到结果。1/5/10 指同一时刻入队的提交数，worker 仍然一次处理一个提交；使用副本中的同一账号与不同源码模拟多个编译工作集。真正跨用户缓存隔离另有单元测试。

示例（仅在已经准备好隔离沙箱、现有配置通过环境安全注入的服务器执行）：

```sh
SOURCE_DATABASE_PATH=/var/lib/cswork/cswork.sqlite \
TEST_WORKER_ENTRY=/path/to/candidate/oj-worker/index.mjs \
GO_JUDGE_URL=http://127.0.0.1:5053 \
TEST_ROUNDS=3 TEST_LANGUAGES=cpp,java,go,python \
node tests/oj-latency-load.mjs
```

冷提交给每份源码加唯一注释；warm 分组先逐份运行预热，测量时记录真实命中，不能假定 warm 一定命中。输出包含每组样本数、P50/P95、错误数、重试数、实际命中数、worker 峰值 RSS。少量突发样本的 P95 不代表线上长期分位数，更不是全题库或 LeetCode 性能保证。

真实浏览器比较还需同网络、同题、同解法、同语言，分别统计运行样例与正式提交，以及冷提交、预编译命中和重复提交。不能拿本脚本时间或结果面板 runtime 冒充用户端指标。

## 保持不变的边界

不减少测试点、不共享学员进程、不更改优化等级/JIT 或单测试资源限制。当前 2 CPU / 4GiB 沙箱和单提交 worker 并发保持不变。10 人同时冷提交仍然会排队；缓存优化不等于扩容。

## 2026-09-08 UTC 实测

完整分组数据见 [JSON 记录](oj-feedback-load-2026-09-08.json)。基线为线上 `8aafc40`，候选为 `c3809a3` 的运行时代码。相同主机、镜像、2 CPU / 4GiB 限制和全部 28 测试；每组一次突发，因此 10 样本的 nearest-rank P95 等于该批最慢提交，不是长期线上 P95。

|10 份同时提交，提交前逐份运行预热|基线 P50 / P95|优化后 P50 / P95|实际缓存命中|
|---|---:|---:|---|
|C++|12.472 / 24.755 秒|5.128 / 10.223 秒|0/10 → 10/10|
|Java|19.060 / 38.254 秒|12.796 / 25.588 秒|0/10 → 10/10|
|Python|5.520 / 10.972 秒|5.517 / 11.008 秒|不缓存解释执行，基本不变|
|Go|旧版因只读缓存 trim 错误，未纳入可比基线|5.560 / 11.147 秒|优化版 10/10|

C++、Java 的主要收益来自消除缓存抖动，最慢反馈分别减少约 59%、33%。冷并发仍受单 worker 约束：10 份 C++ 冷提交最慢 24.424 → 24.511 秒，没有改善。不能把预热结果说成冷提交或所有场景都已达到 LeetCode。

单份提交仅作诊断样本：C++ 冷提交 2.670 → 2.464 秒，warm 1.119 → 1.027 秒；Java 冷 4.117 → 3.770 秒，warm 2.674 → 2.538 秒；修复后 Go 冷 1.395 秒、warm 1.124 秒。均不含公网、API 和渲染，不能直接与浏览器测得的 LeetCode 时间相减。

基线 C++/Java/Python 共 96 份计量提交；候选四语言共 128 份计量提交及 64 份预热提交，全部 28/28，候选错误和重试均为 0。候选 worker 采样峰值 RSS 165472 KiB（约 162MiB），不是理论最大值或整个沙箱总内存。缓存保留预算之外，尚有在途产物、编译进程和结果数据的内存。

Go 原生回归额外验证：种子确实存在，2341 个叶子链接、2600 个私有目录项，16384 inode 中余 13782；强制旧 trim 标记、同源码重复编译、改源码及 gzip/sha256/png 导入成功，错误源码仍报告 CE，共享种子的完整 SHA256 摘要前后不变，`/tmp` 保持 256MiB。

未采纳的实验：仅把测试点并发 2 → 4（仍 2 CPU）对 Java 没有明显收益；C++/Python 仅约一成改善。本轮不因此增加运行并发或替换判题镜像。后续若要求 10 人冷提交也在 3.5 秒内反馈，需要单独评估独立评测容量，而不是继续靠缩短查询间隔。
